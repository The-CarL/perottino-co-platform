# Projects, source and handoffs

Platform source, infrastructure definitions, build scripts and tests ship together on `feature/reproducible-ceo` in the platform repository through a single PR to `main`. Employee-built applications use the projects repository. [Platform deployment PR](https://github.com/The-CarL/perottino-co-platform/pull/1)

A project belongs to an accountable employee and starts under a work goal. Its record holds its ID, repository, application path, originating goal and most recent committed handoff. An owner, CEO or accountable employee can attach a later goal, so a change request can continue the original application. An employee with an active, assigned task on an attached goal can publish the work. The project retains its identity when the employee process restarts.

## Publish a change

1. Create a project for a new application using `project.create`. All applications share the configured Git repository. To change an existing application, find its project with `project.list` and `project.get` and attach the change goal with `project.attach`.
2. When `latestHandoff` is null, submit the initial application files with `project.commit` and omit `baseSha`. The Git worker resolves the repository default branch. When a prior handoff exists, read `project.snapshot` with its project ID, producing task ID and exact commit SHA. The snapshot is a durable copy of the exact UTF-8 files submitted in the acknowledged Git commit.
3. Submit the full project tree with `project.commit` from the current assigned task. For an update, supply the prior SHA as `baseSha`. The tree accepts at most 64 regular text files and 64 KiB of paths and content. Omitting an old file removes it from the new tree. A stale base returns a conflict. Concurrent submissions that both reach Git retain their separate PRs, and the handoff that loses the project update is marked `diverged`.
4. Inspect the returned branch, SHA and PR along with the accountable goal, authoring employee and task. Use `delivery.build` and `delivery.preview` against that SHA. The delivery service records its test result and preview URL. `project.history` retains prior handoffs and `delivery.status` retrieves the corresponding deployment record.

## Review and merge a project PR

A producing employee supplies the project ID, task ID and commit SHA in the handoff. The task’s designated reviewer can review the code, or a manager can assign an independent contributor a review task under a goal attached to the same project. The contributor claims their own review task. Both reviewers use the producing task ID when inspecting the handoff or recording a decision. The worker supplies its current review assignment to the broker.

1. Read the submitted files with `project.snapshot` and the build result with `delivery.status`. Check that the tests exercise the shipped code.
2. Call `project.review` with `projectId`, `taskId`, `commitSha`, a `decision` of `approve` or `changes`, and a concise `note`. Each decision records the authenticated employee and reviewed SHA. A request for changes supersedes an approval for that revision.
3. When the work calls for a merge, call `project.merge` with the same three identifiers. The broker requires the latest approved handoff and its passing build, and verifies the merging employee is independent of the author. Check `project.review.status` for the decision and merge receipt. Task acceptance and production release each have their own operation. A preview-only assignment ends with the preview and open PR.

With a separate GitHub reviewer identity configured, the Git worker submits a formal approval or request for changes on the reviewed SHA. With only the projects PAT, it posts the employee’s decision as a GitHub review comment. The employee ID, decision and reviewed SHA are visible on the PR. The written reasoning stays in the company workspace. Protected branches that require a GitHub approval still need an eligible GitHub reviewer. After enrolling the separate reviewer, record a fresh review of the current revision to submit its formal decision. The projects PAT performs the merge through GitHub’s ordinary PR endpoint. The platform records who requested the merge and the resulting merge SHA. Rejected branch rules or merge conflicts leave the PR open. [GitHub PR merge](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)

## Hosted Git worker

The deployed Git worker reads the raw fine-grained PAT from the Secrets Manager ARN in `PEROTTINO_PROJECTS_GIT_SECRET_ARN`. Grant only reference to that secret on the Git worker role. The broker may invoke the Git worker and receives its commit/PR receipt. The employee and code-test runtimes have no Git secret permission.

Set `PEROTTINO_PROJECTS_REPOSITORY` on the worker and broker to a GitHub `owner/name`. The default is `The-CarL/perottino-co-projects`. The owner selects the repository visibility. Source and PRs are publicly readable when the chosen repository is public. Initialize its default branch with a commit and grant the PAT access to that repository with Contents and Pull requests read/write and Metadata read. Reserve the `jobs/` branch namespace for the worker. Keep production deployment credentials out of workflows that the projects repository runs on these branches. [GitHub fine-grained PAT permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)

The hosted worker uses GitHub’s Git Data and Pull Requests APIs. Each job builds an isolated Git tree, replaces only `apps/<project-id>`, writes a child commit with its original date, and creates `jobs/<project-id>/<job-id>`. The worker verifies the branch tip and reconciles an existing PR on retry. The separate executor runs the submitted tests. The Git worker merges through the PR endpoint after broker authorization. A first PR targets the default branch. A follow-up uses the prior handoff’s commit as its parent even when an earlier PR is still open. Infrastructure proposal files may be included for review under the project path. Policy and deployment changes to the platform remain in its separately permissioned repository. [Git trees](https://docs.github.com/en/rest/git/trees) · [Pull requests](https://docs.github.com/en/rest/pulls/pulls)

## Provision or recover the credential slot

Deploy the [credential stack](github-pat.yaml) in the target account and region. Pass its `ProjectsGitTokenArn` output to the hosted configuration as `projectsGitSecretArn`. The owner can populate the slot later. In Secrets Manager, edit the secret value in **Plaintext** and enter the token itself. Keep the value out of CloudFormation parameters, project files and logs.

If a previous deployment retained the slot, record its full ARN using `DescribeSecret`. If it is in the recovery window, use `RestoreSecret` and verify that its deletion date has cleared. Preserve its existing versions. To adopt it into a new tagged stack, first create the stack with its final project tags and an empty resource set. A template can declare a conditional `AWS::CloudFormation::WaitConditionHandle` with a false condition for this step. Keep that declaration while importing `ProjectsGitToken` from the credential template, using the full secret ARN as the resource identifier `Id` and its existing retention policies. Leave tags and outputs unchanged during the import. Review the change set for exactly one `Import` action and confirm the physical ARN after execution. Then update the stack to the repository template, verify the ARN output, and enable termination protection. [Import resources into a stack](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/resource-import-existing-stack.html)

## Enroll the GitHub reviewer

The credential stack creates a separate retained, empty Secrets Manager secret, `/perottino-co/github/reviewer`. Pass its `ProjectsGitReviewerSecretArn` output as `projectsGitReviewerSecretArn` in the hosted configuration. Only the trusted Git worker reads it. Existing installations with only the writer PAT continue to post attributed review comments. GitHub branches requiring a native approval count approvals from eligible independent GitHub identities.

For a company-owned reviewer, register a GitHub App with repository **Pull requests** set to **Read and write** and the webhook disabled. Install it only on the projects repository. Record the App ID from its settings and the installation ID from the installation settings URL. Generate an RSA private key in the App settings. In Secrets Manager’s **Key/value** editor add `appId`, `installationId` and `privateKey`; paste the entire multiline PEM in the last value. The resulting secret is a JSON object. The worker exchanges that key for a short-lived installation token scoped to the projects repository and its pull requests. [Register a GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app) · [Install a GitHub App](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app)

Alternatively, an eligible collaborator with write access to the projects repository can issue a fine-grained PAT scoped to that repository with **Pull requests** set to **Read and write**. Store the raw token in the reviewer secret as **Plaintext**. GitHub must recognize a different account from the one opening the PR. After enrollment, have the assigned reviewer review the current commit again to publish its native decision. The portal records the platform employee, the commit and the GitHub review link.

## Local verification

The local backend creates a real bare Git repository under the data directory. Each job uses a private temporary Git index and records its commit, task branch and local review ref. A local review has `local: true` and no external URL. A fresh broker can open the same SQLite state and Git directory to continue the project.

Run `node --test test/company-projects.test.mjs test/project-git.test.mjs` to verify the local commits, authorizations, base checks, response-loss recovery, cross-goal handoff and the hosted HTTP contract with an offline GitHub fixture. These tests make no external GitHub requests.
